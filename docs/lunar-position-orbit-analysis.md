# 月球位置偏差与轨道渲染问题 — 根本原因分析与方案

## 一、问题概述

| 问题 | 现象 | 影响范围 |
|------|------|----------|
| 月球位置偏差 | 2020-01-10 月全食时，月球位置与 NASA 实际数据存在约 1~2 天偏差 | 全局（严格/演示尺度均存在） |
| 月球轨道未闭合 | 真实尺度下，月球轨道线首尾存在可见间隙 | 严格物理尺度下最明显 |

## 二、问题一：月球位置 ~2 天偏差的根本原因

### 2.1 当前模型分析

当前 `OrbitEngine.getLunarRelativePositionRaw()` 实现了一个**简化二体开普勒模型**：

```
半长轴  a = 0.00257 AU（固定）
偏心率  e = 0.0549（固定）
倾角    I = 5.145°（固定）
平均近点角 M = (135 + n·days) mod 360, n = 13.176396°/天
近地点黄经 ω = (318.15 + 0.1114·days) mod 360
升交点黄经 Ω = (125.08 - 0.05295·days) mod 360
```

这是一个**"平均轨道根数"**模型——即假设月球在一个缓慢进动的椭圆轨道上运动，只考虑了轨道面的长期进动，完全没有考虑太阳引力对月球造成的**周期性强摄动**。

### 2.2 缺失的核心摄动项

真实月球运动受到太阳引力的强烈干扰（地月系统本质上是一个受太阳扰动的限制性三体问题）。当前模型缺失了以下主要摄动项：

| 摄动名称 | 振幅 | 周期 | 物理来源 |
|----------|------|------|----------|
| **Evection（出差）** | ±1.27° | ~31.8 天 | 太阳引力使月球轨道长轴方向周期性摆动 |
| **Variation（二均差）** | ±0.66° | ~14.8 天 | 太阳引力导致的短周期距离变化 |
| **Annual Equation（周年差）** | ±0.19° | 1 年 | 地球轨道偏心引起日地距离变化，进而改变太阳摄动强度 |
| **倾角章动（Nutation）** | ±0.0025° | 18.6 年 | 地球自转轴摆动，改变月球轨道面相对黄道面的夹角 |
| **J₂ 摄动** | 微小但累积 | 长期 | 地球赤道隆起对月球的长期引力拖曳 |

**关键数字**：月球平均运动速度约 **13.176°/天**。仅 **Evection** 一项就会造成 **±1.27°** 的摆动，对应时间误差约 **±2.3 小时**；加上 **Variation** 的 **±0.66°**、初始历元偏差和长期项累积，在特定日期（如 2020-01-10）的位置偏差可达 **1.5°~2.5°**，对应 **2.7~4.5 小时**。

然而用户观察到的是 **1~2 天的偏差**。这说明除了周期摄动外，还存在**系统性历元偏差**：当前模型使用的 `135°` 初始平均近点角和进动速率是简化值，它们与 J2000 历元的 IAU 标准值之间存在系统性偏移。在 20 年（~7300 天）的累积后，这个偏移被放大了。

### 2.3 为什么行星轨道精确而月球不精确？

项目中行星轨道（如地球）使用 VSOP87 级数的简化版本，包含多个周期性修正项，精度在角秒级。而月球轨道目前只用了一个**零阶开普勒椭圆 + 线性进动**，完全没有周期摄动修正。这是精度差异的根本原因。

### 2.4 解决方案对比

| 方案 | 精度 | 实现复杂度 | 数据量 | 适用场景 |
|------|------|------------|--------|----------|
| **A. 完整 ELP-2000 分析历表** | ±0.001°（角秒级） | 高（~1000 项三角级数） | 内嵌常数表 | 专业天文软件 |
| **B. DE440/DE441 数值历表插值** | ±0.0001° | 中（需预计算 Chebyshev 系数） | ~10MB 数据文件 | NASA 标准 |
| **C. Meeus 低精度月球算法** | ±0.5°（~1 小时） | 低（~20 项修正） | 纯代码，无外部数据 | 科普/教育应用 |
| **D. JPL Horizons 预采样本** | ±0.0001° | 低（查表 + 线性插值） | ~100KB/10 年 | 固定日期范围 |

**推荐方案：C（Meeus 低精度算法）+ D（固定日食数据查表）的混合策略**

对于本项目（科普教育），不需要角秒级精度。Meeus《Astronomical Algorithms》第 47 章的"低精度月球位置"算法仅需约 20 个三角修正项，即可将精度提升到 **±0.5°** 以内（对应误差 **~1 小时**），足以满足月食/日食演示需求。

**具体实施步骤**：

1. **短期（当前可用）**：保留现有模型，扩展 `getLunarRelativePositionRaw()` 增加 Meeus 算法的主要修正项：
   - Evection: `+1.27° · sin(2D - M_m)`
   - Variation: `+0.66° · sin(2D)`
   - Annual Equation: `+0.19° · sin(M_s)`
   - 其中 `D` 为日月平距角，`M_m` 为月球平近点角，`M_s` 为太阳平近点角

2. **中期**：在 `src/data/` 下增加一个预计算的 JPL Horizons 月球位置表（覆盖 1900-2100 年，每天一个样本），运行时通过线性插值获取精确位置。数据量约 **200KB**。

3. **长期**：如需更高精度，可引入 ELP-2000 的简化版本（保留前 100 项）。

## 三、问题二：真实尺度下月球轨道未闭合

### 3.1 现象描述

在严格物理尺度下，月球轨道线（`moon-orbit-line`）的首尾之间存在可见间隙，轨道未形成闭合椭圆。

### 3.2 根本原因

查看轨道绘制代码：

```typescript
for (let j = 0; j <= samples; j++) {
    const days = baseDays + (j / samples) * 27.32166;
    const moonRel = OrbitEngine.getLunarRelativePositionRaw(days);
    // ...
}
```

**问题**：代码在一个恒星月（27.32166 天）内均匀采样，但**每个采样点使用了该时刻的瞬时轨道根数**。由于 `getLunarRelativePositionRaw()` 中的近地点黄经和升交点黄随时间线性变化：

```
periDeg = (318.15 + 0.1114 · days) mod 360   // 近地点进动：0.1114°/天
nodeDeg = (125.08 - 0.05295 · days) mod 360  // 交点退行：-0.05295°/天
```

在 27 天内：
- 近地点进动了 **3.0°**
- 升交点退行了 **1.4°**

这意味着 `j=0`（days = baseDays）和 `j=1000`（days = baseDays + 27.32166）使用的椭圆参数**完全不同**。轨道平面在这 27 天内已经发生了旋转，所以首尾不可能重合。

**这不是 bug，而是模型物理特性的直接反映**：真实的月球轨道确实在进动，一个恒星月后月球回到了惯性空间中的同一位置，但轨道椭圆本身已经转了约 3°。

### 3.3 为什么演示尺度下不明显？

演示尺度下轨道被放大了约 117 倍，视觉上半径约 6.6 场景单位。虽然绝对间隙也被放大了 117 倍，但间隙相对于轨道周长的比例不变（约 3°/360° ≈ 0.8%）。加上轨道线较粗、颜色较淡，人眼不易察觉。

在严格尺度下，轨道半径仅约 **0.056 场景单位**（地球半径约 0.001），轨道线极细，任何间隙都会非常显眼。

### 3.4 正确的可视化语义

在 3D 可视化中，"轨道线"表达的是**某一时刻月球轨道所处的几何平面和形状**，而不是**月球在过去 27 天内走过的实际轨迹**（后者是一个空间中的玫瑰线/进动曲线，非常复杂）。

因此，正确的绘制方式应该是：
- 使用**同一组轨道根数**（当前时刻的根数）
- 在一个完整的 360° 周期内均匀采样
- 绘制一个数学上严格闭合的椭圆

### 3.5 修复方案

在 `OrbitEngine` 中新增一个专门用于**轨道可视化**的函数，它固定使用当前历元的轨道根数，不解开普勒方程遍历时间，而是直接遍历真近点角：

```typescript
static getLunarOrbitPoints(
    days: number,
    samples: number
): { x: number; y: number; z: number }[] {
    // 1. 获取当前历元的瞬时轨道根数
    const moonA = 0.00257;
    const e = 0.0549;
    const iRad = (5.145 * Math.PI) / 180.0;
    const periDeg = (318.15 + 0.1114 * days) % 360;
    const nodeDeg = (125.08 - 0.05295 * days) % 360;
    const omega = ((periDeg - nodeDeg) * Math.PI) / 180.0;
    const node = (nodeDeg * Math.PI) / 180.0;

    // 2. 预计算旋转矩阵
    // ... (与现有代码相同)

    // 3. 遍历真近点角（0 到 2π），绘制闭合椭圆
    const points: { x: number; y: number; z: number }[] = [];
    for (let k = 0; k <= samples; k++) {
        const f = (k / samples) * 2 * Math.PI;
        const r = moonA * (1 - e * e) / (1 + e * Math.cos(f));

        const xOrbit = r * Math.cos(f);
        const yOrbit = r * Math.sin(f);

        // 使用当前历元的固定根数进行坐标旋转
        // ... (与现有代码相同的旋转逻辑)

        points.push({ x, y, z });
    }
    return points;
}
```

**修改点**：
- `src/engine/OrbitEngine.ts`：新增 `getLunarOrbitPoints()`
- `src/components/UniverseViewer.tsx`：在轨道线初始化（~2329）和动态更新（~3267）两处，将 `getLunarRelativePositionRaw()` 替换为 `getLunarOrbitPoints()`
- 确保 `j=0` 和 `j=samples` 使用完全相同的根数，数学上严格闭合

## 四、当前 deltaLon 补偿的局限性

目前代码中使用的 `getLunarDeltaLon()` 补偿（在月食演示模式下将月球强制旋转到地日反方向）是一个**演示层 hack**，它仅解决以下场景：
- 用户在**月食演示面板**中选择了一个具体的月食事件
- 时间轴被强制锁定到该事件的初亏~复圆区间
- 在该区间内，月球被旋转到"看起来正确"的位置

**局限性**：
1. 退出演示模式后，补偿消失，月球回到有偏差的位置
2. 补偿只在**食甚时刻**精确，在初亏/复圆时刻精度下降
3. 对于未列在事件表中的日期（如用户自由探索时间），没有补偿

这进一步说明：根本解决方案是提升轨道计算精度，而不是在渲染层做后处理补偿。

## 六、验证方法

1. **轨道闭合性验证**：在严格物理尺度下，地球视角观察月球轨道，确认首尾完美衔接
2. **位置精度验证**：对比 2020-01-10 19:11 UTC 的月球位置与 JPL Horizons 数据
   - 当前模型偏差：~1.5°~2.5°
   - Meeus 算法目标偏差：~0.5°
   - 查表插值目标偏差：~0.001°
3. **日食/月食检测验证**：用 `detectEclipse()` 函数测试多个已知日食/月食日期，统计误报/漏报率
